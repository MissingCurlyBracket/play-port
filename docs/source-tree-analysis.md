# play-port - Source Tree Analysis

**Date:** 2026-07-05

## Overview

play-port is a single npm package containing two deployable parts: a React SPA
(`src/`) and an AWS Lambda API (`functions/`). Configuration for both lives at
the repository root and is shared where possible (root `package.json`,
`tsconfig.*`, ESLint). Generated documentation lives in `docs/`.

## Multi-Part Structure

This project is organized into 2 distinct parts:

- **Frontend SPA** (`src/`): The user-facing single-page application.
- **Serverless API** (`functions/`): Stateless TMDB/OMDb proxy running on Lambda.

## Critical Directories

### `src/api/`

**Purpose:** Typed HTTP boundary between the SPA and the backend.
**Contains:** Six client classes (`SearchApi`, `TitleApi`, `ProviderApi`, `RegionApi`, `TrendingApi`, `PopularApi`), each with an exported interface + response type. `PopularApi.test.ts` is the sole unit test.
**Integration:** Every client reads `import.meta.env.VITE_API_BASE_URL` and `fetch`es the backend. This is the single place the frontend touches the network.

### `src/components/`

**Purpose:** Atomic-design UI library.
**Contains:** `atoms/` (15 `Base*` MUI wrappers + `LoadingSpinner`/`SkeletonCard`), `molecules/` (7 composed pieces), `organisms/` (`PreferencesDialog`), `templates/` (`MainPageTemplate`).

### `src/routes/`

**Purpose:** File-based routing; each route is a thin container that pulls API clients from router context, prefetches with React Query in a `loader`, and renders a presentational page.
**Entry Points:** `__root.tsx` (layout), `index.tsx` (`/`), `title/$type/$id.tsx` (`/title/$type/$id`), `dev/bones.tsx` (`/dev/bones`).

### `src/pages/`

**Purpose:** Presentational page components (`MainPage`, `TitlePage`) that receive data + callbacks as props — no direct data fetching, which keeps them easy to test/preview.

### `src/mocks/`

**Purpose:** MSW dev mocking. `browser.ts` sets up the worker; `handler.ts` defines fixtures for every backend endpoint (search adds a 2s delay so skeleton loaders are visible).

### `functions/`

**Purpose:** The entire backend.
**Contains:** `handler.ts` exports one async function per endpoint; each proxies TMDB (and OMDb for detail endpoints).
**Entry Points:** Handlers are wired to HTTP API routes in `serverless.yml`.

## Integration Points

### web → backend

- **Location:** `src/api/*.ts`
- **Type:** HTTP `GET` (JSON over `fetch`)
- **Details:** Base URL from `VITE_API_BASE_URL`; region/provider preferences forwarded as query params. In dev, intercepted by MSW instead of reaching Lambda.

### backend → TMDB / OMDb

- **Location:** `functions/handler.ts`
- **Type:** Outbound HTTPS `fetch`
- **Details:** TMDB v3 with `Authorization: Bearer ${TMDB_READ_ACCESS_TOKEN}`; OMDb via `?apikey=`.

## Entry Points

### Frontend SPA

- **Entry Point:** `src/main.tsx`
- **Bootstrap:** Instantiates `QueryClient` + six API clients, builds the router with those in context and hash history, wraps in `ThemeProvider`/`CssBaseline`/`QueryClientProvider`, and (in DEV) starts the MSW worker before rendering.

### Serverless API

- **Entry Point:** `functions/handler.ts`
- **Bootstrap:** No bootstrap — each export is an independent stateless Lambda handler invoked by API Gateway.

## File Organization Patterns

- **Atomic design:** UI split into atoms → molecules → organisms → templates; pages compose templates.
- **Base* wrappers:** MUI primitives are wrapped as `Base*` atoms so styling/props are centralized.
- **Client-per-resource:** one API class per backend resource, each with an interface for DI/mocking.
- **Container/presentational split:** routes fetch data; pages render props.

## Key File Types

### React components

- **Pattern:** `src/components/**/*.tsx`, `src/pages/*.tsx`
- **Purpose:** UI. Function components with hooks.

### Routes

- **Pattern:** `src/routes/**/*.tsx`
- **Purpose:** TanStack Router file routes; `routeTree.gen.ts` is generated from them.

### API clients

- **Pattern:** `src/api/*Api.ts`
- **Purpose:** Typed backend access.

### Lambda handlers

- **Pattern:** `functions/handler.ts` exports
- **Purpose:** Serverless endpoints.

### Tests

- **Pattern:** `src/**/*.test.ts`
- **Purpose:** Vitest unit tests (currently `PopularApi.test.ts`).

## Asset Locations

No significant binary assets in-repo. Fonts come from `@fontsource/roboto`;
poster/backdrop images are remote TMDB URLs. `public/` holds the MSW service
worker and static files.

## Configuration Files

- **`serverless.yml`**: Backend functions, HTTP API routes, region, esbuild build, env vars.
- **`vite.config.ts`**: SPA build; `base: '/play-port/'`, TanStack Router + Tailwind + React plugins, single manual chunk, `Service-Worker-Allowed` header for MSW.
- **`vitest.config.ts`**: Test runner (`globals: true`, React plugin; jsdom via project defaults).
- **`tsconfig.json` / `tsconfig.app.json` / `tsconfig.node.json`**: Project-references TS setup for the SPA + tooling.
- **`functions/tsconfig.json`**: TS config used by esbuild for the backend bundle.
- **`eslint.config.js`**: ESLint flat config (TS, React, React Hooks, Prettier).
- **`boneyard.config.json`**: boneyard-js skeleton capture config.
- **`.github/workflows/main.yml`**: CI/CD deploy pipeline.

## Notes for Development

- **Never edit `src/routeTree.gen.ts`** — it is regenerated by the TanStack Router Vite plugin.
- New backend endpoints require **both** a handler export in `functions/handler.ts` **and** a function entry in `serverless.yml`, plus a matching MSW handler in `src/mocks/handler.ts` for dev.
- New frontend network calls should go through a `src/api/*` client (add/extend one) rather than calling `fetch` inline, and be injected via router context in `main.tsx` + `__root.tsx`.
